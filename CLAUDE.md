# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Hard rules for Claude in this repo

These override defaults — read them before running anything.

1. **Never start a real training run.** Real configs train for 100k+ steps on multi-A100 nodes — they cost money and burn hours, and a botched config wastes both. When you need to exercise the training path, only ever launch:
   - `configs/dev/dev_config.json` or `configs/dev/ci_config.json` (small `steps`, tiny batch, public dataset), or
   - `configs/examples/pi05_training_config.json` (already a smoke config: `steps: 40`, `batch_size: 2`), or
   - `src/opentau/scripts/fake_tensor_training.py` (uses `FakeTensorContext` from `utils/fake_tensor.py` — no real allocation, just shape inference).

   If you find yourself overriding `--steps` to anything > a few hundred, stop and ask.

2. **Default to the CPU test subset.** Local dev typically has no NVIDIA GPU; running the full suite will fail confusingly partway through GPU-only tests.
   - Local / CI-equivalent: `pytest -m "not gpu and not network" -n auto` — this is what `cpu_test.yml` runs and what should always pass. The `not network` clause excludes live-Hugging-Face-Hub tests, which were quarantined off the gate (#410) because transient Hub 429/connectivity errors were reddening the required check; they now run nightly in `network_test.yml`. If you add a test that downloads from the live Hub, mark it `@pytest.mark.network` (or mock `snapshot_download` / `hf_hub_download`) so it stays off the gate.
   - GPU-only subset: `pytest -m "gpu" -n 0` — only run on a CUDA box; on a Mac/CPU laptop it will fail at fixture setup. This is what `gpu_test.yml` runs nightly. Markers are defined in `pyproject.toml::[tool.pytest.ini_options]`.
   - When CI shows a failure under `-m "gpu"` and you can't reproduce locally, say so explicitly — don't pretend you ran it.

3. **Verify determinism on any change to the training loop or model.** ML bugs hide in stochasticity: a bad change can still produce loss curves that *look* plausible. After touching anything in `scripts/train.py`, `policies/*/modeling_*.py`, `optim/`, `datasets/sampler.py`, or `datasets/dataset_mixture.py` (despite the filenames, the training-path sampler — `HierarchicalSampler` — and its `get_dataloader` wiring live in `dataset_mixture.py`, not `sampler.py`; #503 changed every seeded run's data order from there), run a smoke config twice with the same `seed` and confirm the per-step loss series is bit-identical (not just "close"). Seeding utilities live in `src/opentau/utils/random_utils.py` (`set_seed`, `serialize_python_rng_state`, etc.). If two seeded runs diverge, that's a bug — investigate before claiming the change works.

4. **Prefer `einops` for tensor reshape / permutation / reduction.** `einops` (`>=0.8.0`, already a hard dependency in `pyproject.toml`) makes tensor shape transformations self-documenting; opaque `view` / `reshape` / `permute` / `transpose` / `squeeze` / `unsqueeze` chains are a frequent source of subtle bugs in VLA model code. When writing or modifying tensor manipulation code:
   - Use `einops.rearrange` instead of `.view(...)` / `.reshape(...)` / `.permute(...)` / `.transpose(...)` / `.squeeze(...)` / `.unsqueeze(...)` whenever the operation can be expressed as a named-axis pattern (e.g. `rearrange(x, "b t (h w) c -> b t h w c", h=H)` instead of `x.view(B, T, H, W, C)`).
   - Use `einops.reduce` instead of `.mean(dim=...)` / `.sum(dim=...)` / `.max(dim=...)` when the reduction axes are clearer as named patterns.
   - Use `einops.repeat` instead of `.expand(...)` / `.repeat(...)` / broadcasting tricks with `unsqueeze`.
   - Use `einops.einsum` for non-trivial contractions instead of `torch.einsum` with single-letter indices, since named axes survive copy-paste better.
   - Exceptions where plain torch ops are fine: simple `.flatten()` of a contiguous suffix, single-axis `.sum()` over the last dim, contiguity calls (`.contiguous()`), and shape-preserving ops (`.to(...)`, `.float()`). Don't rewrite these just for the sake of einops.
   - When matching a reference (HuggingFace `transformers`, upstream LeRobot, the original π model code), preserve the existing op style verbatim inside that block — readability gains are not worth diff churn against an upstream reference.

5. **Distributed forward/backward, metric gathers, and dataset partitions must stay consistent across ranks.** FSDP / ZeRO-3 hang at NCCL with mismatched all-gather sizes when ranks disagree on what `forward` does; gathered per-sample results silently desync rows when paired tensors are de-padded independently; a dataset partition drawn per-rank silently leaks validation data. These failure modes are all silent at CPU smoke-test time and manifest only on real multi-rank runs, so the patterns below are mandatory — copy them when extending the relevant code, don't reinvent them:
   - **Per-rank branch decisions that fire collectives must be OR-reduced first.** When a `forward` takes a Python-level branch based on what the local micro-batch contains (e.g. `if has_response: embed_language_tokens(...)` in `embed_prefix`), use `_global_or_branch_decisions` in `src/opentau/policies/pi07/low_level/modeling_pi07_low_level.py` — one SUM all-reduce that both OR-reduces the per-rank decisions and asserts cross-rank presence agreement. Adding a new optional branch in distributed `forward` without going through it (or an equivalent pre-branch all-reduce) is the same bug.
   - **Composite forward units must be a single `nn.Module`.** Bundle multi-component decoder steps (e.g. a backbone layer paired with an action-expert layer) into one `nn.Module` so FSDP's all-gather hook prefetches every sub-component together — like `InterleavedDecoderLayer` in `src/opentau/policies/pi07/gemma3_with_expert.py`. Calling sub-components directly on a separately-wrapped layer (`layer.input_layernorm(...)`, `layer.self_attn.q_proj(...)`) bypasses the hook and triggers mismatched all-gather sizes across ranks.
   - **Per-sample tensors that must stay row-aligned across ranks belong in one `gather_for_metrics({...})` dict call of int tensors.** `accelerate.gather_for_metrics` de-pads the ragged final batch (total samples not divisible by `world_size`) by trimming the gathered result to `gradient_state.remainder`. Splitting the gather per quantity breaks row alignment two ways: (1) tensors and non-tensors trim differently — `gather` trims to `remainder`, the `gather_object` path used for lists (e.g. `dataset_repo_id` strings) does not — so provenance desyncs from the loss rows; (2) even all-tensor calls stay aligned only by relying on every independent trim being identical, an accelerate implementation detail. Build the provenance as int tensors and gather everything in one dict call so a single trim hits every entry, aligned by construction — like the validation per-sample gather in `src/opentau/scripts/train.py` (per-sample MSE/CE sums + counts alongside `dataset_index` and a source index). The failure is silent (per-dataset metrics bucketed under the wrong dataset, not a hang) and the CPU suite can't catch it: the multi-rank de-pad path only fires on >1-rank hardware.
   - **Decisions that must agree across ranks must never be drawn from the global torch RNG — it is rank-dependent by construction.** `set_seed(seed, accelerator=...)` (`utils/random_utils.py`) deliberately offsets the seed by `process_index * 12345` so per-sample draws (image augmentation, optional-key dropout, prompt substitution) are decorrelated across ranks; that offset is load-bearing — fix the consumer, never the offset. The train/val `random_split` used to draw from that global RNG, so every rank partitioned the data differently and each rank's validation frames sat in other ranks' training sets — the gathered `Validation/*` metrics and `running_best` selection ran on partly-memorized data (#498). Use a dedicated `torch.Generator` seeded from `cfg.seed` alone, with a fixed fallback constant for `cfg.seed = None` (`train.py` then never calls `set_seed`, so each process otherwise sits on its own entropy-derived state — the same bug by another route): pattern `val_split_generator` / `DEFAULT_VAL_SPLIT_SEED` in `src/opentau/datasets/factory.py`. Unlike the bullets above, this one is CPU-testable — simulate several `process_index` values in one process and assert the decision is identical (pattern: `test_val_split_is_identical_across_ranks` in `tests/datasets/test_datasets.py`).
   - **A config-drift diagnostic must read both sides through one extractor and compare *effective* values — both halves were review findings on #498.** `warn_if_resumed_split_differs` (`datasets/factory.py`) guards the split contract on resume. Its field list must cover *every* config-visible determinant of the guarded invariant — for the split that is `seed`, per-dataset `val_split_ratio`, and the fields deciding `len(dataset)` (`episodes`, `excluded_episodes`, `revision`; all serialized into the checkpoint's `train_config.json` — the first-pass claim that they weren't recorded was wrong, check the serializer before asserting a field is unavailable). Route additions through the single `_split_determining_fields` extractor, fed both the live `cfg.to_dict()` and the checkpoint's parsed JSON: two hand-maintained lists fail open — a key present on only one side silently drops out of the diff, which is indistinguishable from a healthy resume. And resolve defaults before comparing (`None`-inherits-the-mixture-default, the way `make_dataset` does): raw-value comparison warns on no-op changes, and a diagnostic that cries wolf gets tuned out, which costs exactly the real detection it exists for.

6. **The PaliGemma SigLIP tower is mixed-dtype — a change to it must be swept across every hand-rolled forward and every entry-point cast.** Since #482, `to_bfloat16_like_physical_intelligence` (`policies/pi0/paligemma_with_expert.py`, `policies/pi05/paligemma_with_expert.py`; `pi05_mem` / `pi07_paligemma` import pi05's) pins the SigLIP patch-embedding conv and position-embedding table to float32 while the rest of the tower is bfloat16 — they are the only float32-master vision weights (openpi parity), and loading them into bf16 params rounds away precision a later `.to(float32)` cannot recover. Two failure modes recurred in that PR's review — each was caught twice — so sweep for both:
   - **Every hand-rolled SigLIP forward needs the float32→encoder-dtype bridge.** Three places implement the embeddings → encoder loop: the patched `SiglipVisionTransformer.forward` in `utils/transformers_patch.py`, `RLDXVideoEncoder` (`policies/pi05_mem/rldx_video_encoder.py`), and `SpaceTimeSiglipVideoEncoder` (`policies/pi07/video_encoder.py` — the *default* pi05_mem encoder and pi07_paligemma low-level's). A dtype or forward-semantics change to the tower must land in all three; fixing only the transformers patch crashes the others at serve time. Copy the existing pattern: key the encoder dtype off `post_layernorm.weight.dtype` (a wrapped SpaceTime layer's first parameter can be a temporal module), and cast **before** any temporal-mask build (the mask derives from `hidden.dtype`).
   - **Never blanket-`policy.to(torch.bfloat16)` in a serving/eval/inference entry point — it silently re-rounds the pinned embeddings** (no crash, just lost precision). Route the cast through `to_dtype_preserving_siglip_float32` (`policies/utils.py`; no-op for uniform-dtype towers like Gemma3), as `grpc/server.py`, `robocasa/server.py`, `inference.py`, `eval.py`, `benchmark_inference.py`, `high_level_planner_inference.py`, and `actions_mse_loss.py` do. Intentional exceptions: the training-path casts (`train.py`, `profile_step.py`, `find_unused_params.py` — deferred to #483), the value-policy scripts (`calculate_value.py`, `get_advantage_and_percentiles.py`), which never pin embeddings, and `export_to_onnx.py`, which casts *up* to float32. When adding an entry point that casts a policy, don't grep narrowly and assume the sweep is done — miss-by-omission was the repeated review finding, and it recurred: `robocasa/server.py` predated #482 and was missed by that PR's six-file sweep, so a pi05 checkpoint served to RoboCasa had a different vision tower than the same checkpoint under `eval.py`. The sweep is now machine-checked — `test_serving_entry_point_routes_its_cast_through_the_helper` / `test_no_unlisted_script_casts_a_policy_dtype_directly` (`tests/policies/test_siglip_embedding_dtype.py`) AST-scan `scripts/` and fail on an unlisted policy dtype downcast in any spelling (`.to(dtype=...)`, `.half()`, `.bfloat16()`, `.type(<dtype>)`, on receivers named like a policy/model *or* bound from `make_policy`/`from_pretrained` — see rule 9), so add new entry points to `_ROUTED_ENTRY_POINTS` (or the reasoned `_UNROUTED_CAST_IS_INTENTIONAL` allowlist) rather than to a prose list.

7. **New per-dataset settings must survive the val-split `Subset` wrapper, and dataset-side transforms the policy must invert need a `make_policy` guard.** Both failure modes are silent — the data pipeline keeps producing plausible batches — and both were blocking findings in #485:
   - **When `val_freq > 0`, `make_dataset` wraps each dataset in `torch.utils.data.random_split` `Subset`s, and `Subset` does not proxy attributes.** A `getattr(ds, "my_new_setting", None)` in `WeightedDatasetMixture` construction returns `None` while the wrapped dataset still applies the setting in `__getitem__` — so the mixture publishes nothing (wrongly scaled norm buffers, no inference-time inverse) the moment validation is enabled. Read per-dataset attributes through `_unwrapped_attr` (`datasets/dataset_mixture.py`), which unwraps one `Subset` level like `_instance_name_map` and the `.meta` lookup do, and add a `val_freq > 0` regression test for the new attribute (pattern: `test_val_split_subset_wrapper_preserves_per_dataset_settings` in `tests/datasets/test_dataset_mixture.py`).
   - **The dataset side of a train-time transform is policy-agnostic; the inference-time inverse is not.** If a dataset transform must be inverted at `sample_actions` time (e.g. `use_delta_joint_actions` → the policy re-adds the chunk-start state), `make_policy` must raise when the selected policy config cannot carry the needed field (`delta_action_state_map` guard in `policies/factory.py`) — otherwise the model trains on transformed targets and inference silently emits them untransformed. Pin the guard's invariant across the *whole* policy registry, not a hand-picked subset (see `test_only_delta_capable_policies_carry_the_field_the_factory_guard_relies_on`), so a new config gaining the field without the inverse fails loudly.

8. **A docstring that states a contract must be verified against the implementation, and a test that claims to pin a contract must construct the case that could break it.** Both halves were review findings on #503, a one-line fix whose only new prose and tests concerned the sampler seeding contract (the same class recurred on #505):
   - The new `HierarchicalSampler` docstring stated the `seed`/`generator` precedence backwards — the code applies `seed` *to* the explicit generator via `manual_seed`, so `seed` wins and re-seeds the caller's object in place, the opposite of the "explicit `generator` wins" a reader expects. A docstring that misstates a contract is worse than none: it sends a future caller confidently the wrong way. Verify the claim by *running* the conflicting case, not by re-reading the code.
   - `test_explicit_generator_wins_over_seed` never passed both arguments: it compared two single-argument constructions whose streams match under *either* precedence, so a refactor flipping the precedence would have failed nothing. When documenting or testing behavior at a conflict point (argument precedence, override order, fallback selection), exercise the actual conflict — pass both inputs, assert which one wins, and assert any side effect (pattern: `test_seed_beats_generator_and_reseeds_it_in_place` in `tests/datasets/test_dataset_mixture.py`, which also pins the in-place re-seed of the caller's generator, the surprising direction a refactor would silently flip).

   Same failure class as the unexercised-v0-branch finding in #485 (see the `config_version` notes below): a pin whose passing does not depend on the property it names is not a pin.

9. **A syntax-matching static guard must cover every spelling of the operation it forbids, and the detector itself needs positive *and* negative test cases.** Both halves were review findings on #507's policy-cast AST guard (rule 6), which as first written matched only `.to(...)` calls on receivers whose trailing name contains `"policy"` — leaving two silent escape hatches: `model = make_policy(cfg); model.to(torch.bfloat16)` (same cast, differently-named receiver) and `policy.half()` / `policy.bfloat16()` / `policy.type(torch.bfloat16)` (same downcast by another spelling). A guard whose stated purpose is catching the *next* miss-by-omission fails at exactly that purpose for every uncovered spelling — and it's worse than no guard, because prose now advertises the invariant as machine-checked and reviewers stop sweeping by hand. When writing or extending one: (a) enumerate the semantically-equivalent spellings and flag them all, excluding a spelling only with a stated reason it *cannot* violate the invariant (upcasts `.float()`/`.double()` cannot round the pinned tables); (b) don't key on receiver naming alone — also track names bound from the producer calls (`make_policy(...)` / `from_pretrained(...)`; pattern `_policy_bound_names` in `tests/policies/test_siglip_embedding_dtype.py`); (c) parametrize the detector over each covered spelling plus the cases it must keep ignoring (tensor casts like `batch["state"].to(dtype=...)`, device-only `.to(device)`), so widened coverage is itself pinned rather than an untested claim — rule 8's failure class in lint form (pattern: `test_cast_detector_covers_the_spellings_a_future_entry_point_could_use`).

## Project overview

OpenTau is Tensor's open-source PyTorch training toolchain for vision-language-action (VLA) models — a fork of LeRobot with extra capabilities (heterogeneous-dataset co-training, discrete actions for π₀.₅, knowledge insulation, dropout in PaliGemma, π*₀.₆-style RL, validation splits, profilers). Any LeRobot-compliant policy and dataset works directly. Pinned to **Python 3.10**.

## Environment & install

Dependency management is **`uv` (>= 0.8.4) only** — `pyproject.toml`/`uv.lock` are authoritative; do not edit `requirements.txt` (none exists) or call `pip install` against the env. The `>= 0.8.4` floor is enforced by `required-version` in `[tool.uv]` and is needed because `[tool.uv].extra-build-dependencies` (which injects `cmake` into `egl-probe`'s PEP 517 build isolation so its sdist builds without a system cmake, on CMake 4) is only honored by uv 0.8.4+.

```bash
uv sync --extra dev --extra libero          # standard dev setup (matches CI)
uv sync --all-extras                         # everything (libero + robocasa + urdf + trt co-resolve into one env on the shared robosuite-1.5 master / numpy 2.x stack); the trt extra is marker-gated, so it installs TensorRT only on linux/win x86_64 and a macOS sync just skips it
source .venv/bin/activate
```

Re-run `uv sync` whenever `pyproject.toml`/`uv.lock` change. Add deps with `uv add <pkg>`; lock with `uv lock`.

Installable extras: `dev` (pre-commit, sphinx, pytest), `libero` (sim env — pulls a forked LIBERO from `shuheng-liu/LIBERO`, on robosuite 1.5 master + numpy 2.x + gymnasium), `robocasa` (RoboCasa365 kitchen sim — co-installs with `libero` on the shared robosuite stack; see the RoboCasa365 note below), `urdf` (rerun ≥0.28, numpy 2.x), `trt` (TensorRT, Linux/Win x86_64 only).

**RoboCasa365** (`envs/robocasa.py`) is a first-class extra that co-installs with `libero` on a shared robosuite stack: `uv sync --extra robocasa`. Two non-obvious things make it resolve: (1) robocasa needs `MujocoEnv(load_model_on_init=...)`, added on robosuite **master** *after* the 1.5.2 PyPI release, so `[tool.uv.sources]` repins `robosuite` to a master commit — which still self-reports "1.5.2" (matching the extras' pins) and is validated to also run LIBERO; (2) robocasa is pulled from the `shuheng-liu/robocasa` packaging fork (mirroring the `shuheng-liu/LIBERO` / `egl_probe` forks) that drops upstream's `lerobot==0.3.3` / `tianshou` / `opencv-python` / `hidapi` deps and loosens its `numpy`/`numba`/`scipy`/`mujoco` pins + import-time version asserts, since uv can't `--no-deps` a single package in a lock. Kitchen assets (~5-10GB) **auto-download on the first RoboCasa env build** into a venv-external, relocatable store (defaults to `$HF_OPENTAU_HOME/robocasa/assets`, overridable via the `ROBOCASA_ASSETS_ROOT` env var or the new `env.assets_root` config field) — so ephemeral `uv` venvs don't lose or re-fetch them; the download is rank-0-gated with a cross-rank barrier (`_ensure_robocasa_assets` in `envs/robocasa.py`). To warm the cache up front (e.g. on a login node before a multi-rank eval), run `python -m opentau.scripts.download_robocasa_assets`. Run headless with `MUJOCO_GL=egl`. NOTE (a platform/toolchain constraint, not an extras conflict — all extras co-resolve into one environment): a full `uv lock` (universal resolution) must run on Linux because the `trt` extra's TensorRT sdist can't build on macOS arm64. `uv sync` from the committed lock works anywhere — the marker-gated `tensorrt` is simply skipped on non-linux/win platforms, so even `uv sync --all-extras` resolves on macOS (just without trt).

### Training / eval / export (console scripts)

`pyproject.toml` defines four console entry points that wrap `accelerate launch` (defined in `src/opentau/scripts/launch.py`):

```bash
# Single-node multi-GPU training (uses 8 GPUs by default — edit num_processes)
opentau-train \
    --accelerate-config configs/examples/accelerate_ddp_config.yaml \
    --config_path=configs/examples/pi05_training_config.json

opentau-eval --accelerate-config <yaml> --config_path=<json>      # eval
opentau-export --config_path=<json>                                # ONNX export (no accelerate)
opentau-dataset-viz --config_path=<json>                           # dataset visualizer (no accelerate)
```

Configs are **draccus-based JSON** (see `configs/examples/`). Any field can be overridden on the CLI: `--policy.type=pi05 --batch_size=8 --steps=1000`. Use `pi_config.json` style for π₀, `pi05_*.json` for π₀.₅. Accelerate configs: `accelerate_ddp_config.yaml` (DDP) or `accelerate_deepspeed_config.yaml` (ZeRO).

Direct invocation (bypasses the launcher; useful in slurm/sbatch wrappers): `accelerate launch --config_file <yaml> src/opentau/scripts/train.py --config_path=<json>`.

### Diagnostics

Three drop-in profiling scripts read the same `TrainPipelineConfig`:

- `src/opentau/scripts/profile_step.py` — per-step wall-clock breakdown (forward / backward / optimizer / sync)
- `src/opentau/scripts/profile_dataloader.py` — dataloader-only ceiling, no model
- `src/opentau/scripts/find_unused_params.py` — lists params that DDP would drop with `find_unused_parameters=False`

`FIND_UNUSED_PARAMS=false` (env var, read in `train.py`) reclaims ~10-15% of step time once a config has been audited.

For *hung* runs (NCCL collective stuck, dataloader worker wedged in a C extension, anything `debugpy` can't reach), `py-spy` is in the `dev` extra. `py-spy dump --pid <pid>` attaches non-cooperatively and prints the Python stack of every thread — pair with `pgrep -f 'opentau/scripts/train.py'` to find ranks. Run as the same user as the target on Linux (no `sudo` typically needed); on macOS, prefix with `sudo` (Apple ptrace restriction).

## Architecture

### Configuration system (draccus)

Everything starts from a `TrainPipelineConfig` (`src/opentau/configs/train.py`) decorated as a draccus dataclass. The `@parser.wrap()` decorator on `train()` / `eval()` is OpenTau's extension over draccus that supports loading a config from a local path or HuggingFace Hub via `--config_path=...`, then merging in CLI overrides. The pattern is **never instantiate config objects directly in scripts** — always go through `parser.wrap` so that hub paths, plugin discovery (`PLUGIN_DISCOVERY_SUFFIX = "discover_packages_path"`), and CLI overrides all flow correctly.

**Checkpoint paths accept a `repo_id@revision` suffix.** Published checkpoints are one HF repo per run with each saved step as a git tag and `main` at the highest step, so `--policy.path=TensorAuto/<runid>-<runname>@6000` loads that step and a bare repo id loads the latest. It works for `--policy.path`, `--config_path` and `policy.pretrained_path` alike because the split happens at the four loader chokepoints (`PreTrainedConfig.from_pretrained`, `TrainPipelineConfig.from_pretrained`, `PreTrainedPolicy.from_pretrained`, `_peek_config_version`) rather than at the call sites — `make_policy` and the eight direct `from_pretrained` callers pass the spec straight through as a string. **The invariant most likely to get broken: a local path is NEVER split.** `split_repo_revision` (`utils/hub.py`) short-circuits on `os.path.exists` and refuses to split anything path-shaped (leading `/`, `.`, `~`, a backslash, or more than one `/`), because checkpoint dirs legitimately contain `@` and a *moved* local path must still fail as a path rather than as a bogus repo id. It is also idempotent — nested `from_pretrained` calls re-split their own output — and raises when an `@` suffix and an explicit `revision=` disagree. Don't normalize `cfg.pretrained_path` in place: the suffix has to survive into the serialized config. All weight resolution goes through `resolve_pretrained_weights_file` (`policies/pretrained.py`); the only tolerated failure is `CheckpointWeightsNotFoundError` from a **local dir** (the DeepSpeed/ZeRO resume shape), and AST tests over the whole policy registry (`tests/policies/test_from_pretrained_revision_overrides.py`) pin that no override grows its own `cached_file` resolver or reads its own keyword-only params out of `**kwargs` again. That fail-loudly rule covers *resolution* only: the later key-remap / `load_state_dict(strict=False)` stage in the seven `from_pretrained` overrides deliberately keeps its broad `except Exception` (warn + return a partially-loaded model). `strict=False` already absorbs key mismatches, so what that catch actually hides is genuine shape conflicts — but tightening it can unmask the documented partial-load warm-start paths (e.g. pi06 warm-starting from a `lerobot/pi05` checkpoint). Don't "fix" it as a drive-by cleanup; per #492 any tightening must land as its own revertible change.

**Every `from_pretrained` must call `resolve_checkpoint_provenance` (`policies/pretrained.py`) immediately before `cls(config)`.** It resolves `config_version` off the weights being loaded (absent tag ⇒ legacy `0`; an explicitly-set value is honored untouched) and runs `validate_input_resolution`. The ordering is load-bearing: `Normalize`/`Unnormalize` are built from `config_version` *during* `cls(config)`, so resolving it afterwards silently leaves them on the wrong convention. This used to live inline in the base class only, and all seven overrides skipped it — and since `make_policy` always passes `config=`, their `if config is None` branch never ran either, so no production policy ever applied the gate. Both the presence and the call-ordering are pinned by AST tests across the registry; a new override that forgets it fails the suite.

Key invariant on `TrainPipelineConfig`: `batch_size == dataloader_batch_size * gradient_accumulation_steps`. When sweeping per-rank batch, override all three together — the validator will reject inconsistent combinations. When using DeepSpeed, `gradient_accumulation_steps` must also match the value in the DeepSpeed JSON.

`PreTrainedConfig` (`configs/policies.py`) is the abstract base for policy configs. Subclasses register themselves via the `policy.type` choice key (draccus `CHOICE_TYPE_KEY`). To add a new policy: subclass `PreTrainedConfig`, subclass `PreTrainedPolicy`, register both in `policies/factory.py::get_policy_class` / `make_policy_config`, export the config from `policies/__init__.py`, and add the name to `available_policies` in `src/opentau/__init__.py` (checked by `tests/test_available.py`).

`config_version` (`configs/policies.py::CURRENT_CONFIG_VERSION`) is a monotonic schema version for **behavioral conventions** the weights were trained under — NOT the package version. Bump it only when a change alters what the model sees/produces and must be gated so old checkpoints keep their trained behavior (v1 = openpi-parity normalization: zero-range MIN_MAX/QUANTILE dims map to `0.0` not `-1.0`, and the normalization epsilon is `OPENPI_EPS` 1e-6 vs legacy `LEGACY_EPS` 1e-8; see `CHANGELOG.md`). The field is `int | None`; `None` behaves as CURRENT for behavior but is resolved to a concrete int automatically — to `0` (legacy) when `PreTrainedPolicy.from_pretrained` loads pre-tag weights (it peeks the source's `config.json`/`train_config.json`), and to CURRENT for a fresh/scratch run (`factory.make_policy` + save concretization). **Never resolve it in `__post_init__`** — that erases the "was the key absent?" signal the loader needs. A gated convention read at forward time must reach `Normalize`/`Unnormalize` as a plain scalar kwarg (`zero_range_center` from `config.zero_range_centers_on_zero()`, `eps` from `config.normalization_epsilon()`) computed once, so it is identical across ranks and constant-folds under compile (CLAUDE.md rule 5). **The `Normalize`/`Unnormalize` modules are not the only implementations of the formula — sweep every hand-rolled mirror when gating a convention, and never let a mirror read the module-level `EPS` default** (it is pinned to the *current* convention, not the checkpoint's): the pi07_paligemma inline discrete-action inverse reads `self.normalize_discrete_actions.eps` / `.zero_range_center` from the module it inverts, and `fit_fast_tokenizer` selects `_normalize_eps_for(--config_version)` — both were missed on first pass in #485's review. Then pin the legacy (non-default) branch with a mutation-killing test: every default-value construction equals the module constant, so an unexercised v0 branch makes a revert to `EPS` invisible to the suite. Fitted FAST tokenizers version-stamp the same convention (`opentau_action_norm.json` sidecar) and a policy raises on mismatch at load.

### Module layout (`src/opentau/`)

- `configs/` — dataclass configs (train, eval, policies, envs, optim, deployment, libero, ros2lerobot)
- `datasets/` — LeRobot-compatible datasets, `WeightedDatasetMixture` (heterogeneous co-training), VQA datasets, v1→v2 / v2→v2.1 converters under `v2/`, `v21/`
- `envs/` — gym/gymnasium envs (LIBERO in `libero.py`, RoboCasa365 in `robocasa.py`); `factory.make_envs()` dispatches per `env.type`. Both return `dict[group][task_id] -> VectorEnv` so the env-agnostic eval pipeline (`scripts/eval.py`) gives per-task success rates + `grid_summary` wandb videos for free.
- `optim/` — optimizer + LR-scheduler dataclass-configured factories
- `planner/` — high-level planner using `prompts.yaml`
- `policies/` — `pi0`, `pi05`, `pi05_mem`, `pi06`, `pi07/{high_level_planner,low_level}` (current π0.7 impl: Gemma 3 backbone + SpaceTime SigLIP video encoder; note `low_level/` — not `low_level_planner/`, since the low-level policy is a controller, not a planner), `pi07_paligemma/{high_level_planner,low_level}` (legacy PaliGemma variant of π0.7 — kept for older checkpoints; a fix targeting π0.7 usually needs to land in `pi07/`, not here), `cosmos3` (frozen Qwen3-VL-32B reasoner from NVIDIA Cosmos3-Super + trainable action expert), `cosmos3_nano` (same modeling code on the 8B Nano reasoner — defaults-only subclass of `cosmos3`), `value`. Each subdir has a `configuration_*.py` and `modeling_*.py`. Vision backbone wrappers: `paligemma_with_expert.py` (pi0/pi05/pi05_mem/pi07_paligemma), `gemma3_with_expert.py` (pi06/pi07), and `cosmos3/qwen3vl_with_expert.py` (cosmos3/cosmos3_nano).
- `scripts/` — entry points (train/eval/launch), profilers, dataset converters (LIBERO, ROS, human video, RECAP), gRPC inference server, ONNX/TensorRT export
- `utils/` — `accelerate_utils` (sets process-global accelerator for rank detection), `train_utils` (checkpoint save/load/prune), `logging_utils` (`AverageMeter`, `MetricsTracker`), `transformers_patch`, `monkey_patch`

### Training loop (`scripts/train.py`)

`train()` is the entry; uses `accelerate.Accelerator` for distributed coordination. Loss is a weighted sum of `MSE` (action regression) and `CE` (discrete-action / language) terms — weights from `cfg.loss_weighting`. Metrics use `MetricsTracker` whose `__setattr__` is **not idempotent** — setting `metrics.loss = x` calls `AverageMeter.update(x)`, so repeat assignments accumulate a running mean rather than overwriting. Every reduction goes through `accelerator.gather_for_metrics` for rank-0 logging.

`save_checkpoint` / `load_training_state` (in `utils/train_utils.py`) handle resume — when resuming, the checkpoint config takes precedence over CLI args. `prune_old_checkpoints` keeps the most recent N.

## PR / contribution workflow

- **Always run pre-commit hooks before running unit tests.** The hooks (ruff format, end-of-file-fixer, trailing-whitespace, pyupgrade) will rewrite files or prompt for fixes; running tests first wastes a run when the formatter then changes the source. Sequence: `pre-commit run --all-files` → `pytest`.
- **Commit messages: keep them simple. The first line must be under 80 characters.** No long preambles in the subject.
- **PRs must follow `.github/PULL_REQUEST_TEMPLATE.md` verbatim.** The `check-pr-checklist.yml` CI grep-matches the exact phrases for the docstring and policy-change checkboxes — do not rephrase them, do not delete sections. Fill in `What this does`, `How it was tested`, and `How to checkout & try`. Create the PR with the full template body from the start (`gh pr create --body-file ...`, never `--fill`/`--fill-first`): the workflow reads `context.payload.pull_request.body` from the *event payload*, not the live PR, so if a template-less body slips in, fixing the body and re-running the failed job just replays the stale payload — only a fresh `edited`/`synchronize`/`reopened` event (a body edit, a push, or a close-and-reopen) re-evaluates it (#492).
- Policy-related PRs require running GPU pytests + nightly regression tests; check both boxes.
- Required tests/lint that gate merge: `cpu_test.yml` (PRs/pushes) and `pre-commit.yml`. `gpu_test.yml` and `regression_test.yml` run nightly on AWS g6 runners (cron 10:00 UTC). `network_test.yml` runs the `network`-marked live-Hub subset nightly too (cron 10:00 UTC, `ubuntu-latest`, serial) — it is **non-gating**, so a Hub flake there can't block a PR.
- Per-file ruff overrides in `pyproject.toml`: gRPC server (PascalCase methods, `N802`), `recordhuman_to_lerobot.py` (math-convention uppercase names, `N803`/`N806`).
- **Claude integration:** three workflows under `.github/workflows/` add bots — `claude-pr-review.yml` does auto-review on PR open/sync (single edit-in-place summary tagged `[claude-review]`), `claude-implement-fixes.yml` handles `@claude fix` and addresses feedback in one coalesced commit (replies tagged `[claude-fix]`), and `extract-claude-lessons.yml` does post-merge lessons extraction into `chore(claude): learn from #N` PRs.
